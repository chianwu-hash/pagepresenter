HTML 簡報分頁品質：Codex 與 Claude 討論整理

這份文件把我們剛剛討論「如何提升 PagePresenter 轉成 HTML 簡報的分頁品質」整理成產品決策。重點不是技術炫技，而是讓你看懂：原本想法哪裡對、哪裡有風險、最後要怎麼做比較穩。

目前 MVP HTML 簡報播放器已可用，但分頁主要還是靠現有 TOC/標題結構。
最大風險 AI 分頁若錨點對錯，會比現在 fallback 更糟，可能造成內容重複、遺漏或亂序。
最後方向 先建立 slide plan 渲染與驗證安全網，再接輕量 AI 分頁，不把它塞進既有大 AI 回應。
背景 討論過程 Claude 主要意見 採納結論 下一步路線 驗證方式

一、背景：MVP 已完成，但分頁品質還不是產品級

目前 PagePresenter 已經有「轉成 HTML 簡報」按鈕，會在現有頁面中用燈箱方式播放 HTML slides。這符合產品定位：快速、頁內可用、不強迫下載。

但目前的分頁方式仍主要依賴既有 DOM 的目錄與標題。這代表：

  • AI 原文版看起來像 AI 分頁，其實多半只是沿用處室目錄。
  • AI 精簡版雖已修掉「套錯原文目錄骨架」的 bug，但仍不是 AI 真正判斷簡報分頁。
  • 現階段可用，但遇到長段落、混合事項或同一處室過長時，簡報感會下降。
結論：播放器 MVP 已經站起來了，下一個真正的產品風險就是「分頁品質」。

二、討論過程：原本想法如何被修正

Step 1

Codex 原始企劃

原本我主張：在既有 AI 處理時，一次產生整理、重點、分頁。這樣按「轉成 HTML 簡報」時不用再呼叫 AI，速度最快。

設想資料是 htmlSlidePlans.simplified 與 htmlSlidePlans.original，每頁有標題、摘要、anchor hints、section refs。

Step 2

Claude CLI 兩次失敗

我用 chat-mode CLI review 送給 Claude，但兩次都卡在 supervisor 需要的 final result event，分類為 malformed_response。因此不能把 partial output 當正式 Claude 意見。

Step 3

Claude Desktop fallback

之後改用 Claude Desktop。中間有 UI 操作失誤與權限提示問題，最後由你手動送出並 bypass，Claude 完成了唯讀 review。

Claude 回覆中也提醒：它看到一則「bypass permissions 模式啟用，請盡量改用 Bash」的訊息，但它認為與我們的 read-only envelope 衝突，因此沒有遵從。

Step 4

Claude 的關鍵反駁

Claude 認為：不要把 slide plan 塞進既有 AI 大回應，因為會讓主功能「AI 精簡、AI 重點」的穩定性承擔分頁功能的風險。

三、Claude 主要意見：哪些地方值得聽

議題 Claude 的看法 我是否採納
開燈箱時呼叫 AI 反對。燈箱應該同步、快速開啟，任何 await 都破壞產品體感。 採納。按「轉成 HTML 簡報」時不呼叫 AI。
把 slide plan 塞進既有 AI 回應 反對。既有格式化/重點契約已經很重，再加 JSON 會增加截斷與解析失敗風險。 採納，並修正原企劃。
原文版 slide plan 原文版不是 AI 生成，而是本機 DOM clone 後做 highlight，所以 plan 應從本機 heading 清單建立。 採納。原文版重點只做「過長處室再切」。
錨定方式 不要靠自由文字 anchor hints 當主鍵，應以 sectionIndex 作為穩定主鍵。 採納。文字 title 只做校驗或顯示。
主題重排 v1 不做非相鄰重排，只允許相鄰合併與過長切分。 採納。避免內容重複、遺漏、順序錯亂。
快取版本 不要 bump 既有 aiCachePromptVersion，否則舊 AI 快取會全失效。 採納。slide plan 使用獨立 aiSlidePlanVersion。

四、最後採納的產品決策

保留：開燈箱不呼叫 AI 使用者按下「轉成 HTML 簡報」時，必須立即進入播放，不等待 AI。
放棄：一次大 AI 回應包全部 原本想節省呼叫次數，但這會讓主要 AI 功能變脆弱，不值得。
改成：背景輕量 slide-plan call AI 處理完成後，用 heading 清單做一個小型分頁規劃，不送全文。
安全網：validator + fallback AI plan 壞掉時，不能比現在更糟；壞區段退回 TOC 分頁。
這裡和我們原先「盡量省 AI 呼叫」的想法有衝突。修正後的判斷是：可以多一個很小的 AI 呼叫，但不能把主 AI 整理/重點功能弄得容易失敗。

最後的 schema 方向

Claude 建議 slide plan 先收斂成很小、很硬的格式：

{
  version: "simplified" | "original",
  planVersion: "2026-xx",
  slides: [
    {
      startSection: 0,
      endSection: 2,
      title: "教務處重點",
      reason: "相鄰短段落合併"
    }
  ]
}

重要的是 startSection 與 endSection，不是自由文字 anchor。這樣 AI 最壞只是切得不漂亮，不會把內容切丟。

五、下一步路線：先不急著接 AI

Claude 最重要的建議是：先建立安全的 plan 渲染管線，再接 AI。也就是先把地基做好，不要一開始就把 AI 接進來。

S0 量化目前分頁品質：頁數、每頁字數、超長頁比例。
S1 把現有 TOC fallback 轉成 slide plan，再由共同 renderer 渲染。
S2 建立 validator：檢查 gap、overlap、越界、重複、空頁。
S3 建立 AI 輸入：只送 heading 清單，不送全文。
S4 接獨立輕量 AI plan call，快取為選用欄位。

建議現在先做 S0-S2

  • S0 讓我們知道現在的分頁到底哪裡不好。
  • S1 是等價重構，使用者看到的結果不變，但架構變乾淨。
  • S2 是保險絲，確保之後 AI plan 壞掉時不會炸掉簡報。

等 S0-S2 完成後，再做 S3-S4 接 AI。這樣每一步都可驗證，不會把問題全部揉在一起。

六、測試與驗證：怎麼知道它真的更好

Claude 建議的驗證重點如下：

validator fallback cache highlight DOM prompt injection
  • Validator 測試：gap、overlap、越界 index、非整數、start > end、空 slides、超長頁。
  • Parser 測試：非 JSON、截斷 JSON、markdown code fence、多餘欄位、title 含 HTML。
  • DOM 測試：同一 plan 套在 normal 與 highlight DOM，heading 數不一致時要降級。
  • 快取測試：舊 AI 快取沒有 slide plan 時仍有效，不要求使用者重跑完整 AI。
  • 手動驗收：AI 精簡、AI 精簡重點、AI 原文、AI 原文重點四種狀態都能開燈箱。
實作時應優先檢查這些位置：content.js 的 buildHtmlSlidesFromCurrentContent()、cloneHtmlSlideRange()、AI cache、prompt 契約、TOC/sections 建構，以及 updateContentDisplay()。

七、用一句話總結

不要急著讓 AI 直接接管分頁；先把分頁變成可驗證的 slide plan，再讓 AI 只做小範圍、可失敗、可 fallback 的分頁建議。

這樣做比較不像一次豪賭，也比較符合 PagePresenter 的產品精神：快速、可靠、不讓 AI 失誤毀掉基本可用性。
